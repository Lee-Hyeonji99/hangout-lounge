# 소셜 라운지(가칭) — 멀티플레이어 채팅 공간 기술 계획

캐주얼하게 모여서 앉아 채팅치고, 먹고, 담배 피고 하는 **가벼운 소셜 공간**.
로블록스처럼 액션/피지컬 동기화가 필요한 게 아니라 "몇 명이 같은 공간에 있다는
느낌 + 음성/텍스트 채팅 + 상태 애니메이션"이 전부라, 전용 게임 서버나 별도 엔진
없이 **이 저장소의 기존 스택(Three.js) + 브라우저 내장 WebRTC**로 충분하다는
결론(지난 대화 참고). 아직 코드는 없음 — 이 문서는 구현 전 설계.

## 1. 스코프 (확정)

- **하는 것**: 3D 공간에 아바타로 들어가서 걸어다니고, 앉기/먹기/담배피기 같은
  상태 애니메이션 트리거, 텍스트 채팅, 음성 채팅.
- **안 하는 것**: 물리 기반 상호작용(밀기/충돌 정밀 동기화), 전투/경쟁 요소,
  수십 명 이상 동접, 서버 권위 검증(치팅 방지) — 친구들끼리 쓰는 캐주얼 공간이라
  "누가 순간이동처럼 보여도 그냥 웃고 넘어가는" 수준의 관대함을 기본으로 한다.
- **동접 목표**: 방 하나에 **최대 12명**. 이 숫자가 아래 "P2P 메시" 선택의 전제다
  (그 이상은 다른 토폴로지가 필요 — 5번 참고).

## 2. 이 저장소의 원칙과의 충돌 지점

`CLAUDE.md`는 "정적 파일이라 빌드/설치 단계 없음"을 기본 원칙으로 한다. 이 게임은
**시그널링 서버 하나만은 예외로 필요**하다(3번 참고) — WebRTC라도 최초 연결
중개(누가 누구와 연결할지)는 어떤 형태로든 서버가 있어야 한다. 순수 정적 파일로는
안 되는 이 저장소의 첫 사례이므로, 구현 시작 전에 이 예외를 `CLAUDE.md`에 명시적으로
기록해야 한다(다른 사람이 "왜 얘만 서버가 있지" 헷갈리지 않게).

## 3. 아키텍처

```
브라우저 A ──┐                      ┌── 브라우저 B
             │   WebRTC DataChannel  │   (위치/상태/채팅 텍스트)
             ├──────────────────────┤
             │   WebRTC Audio Track  │   (음성 — 브라우저 내장 Opus 인코딩)
             │                       │
             └──── 최초 연결 중개만 ──┘
                   (시그널링, 아래 3-a)
```

- **P2P 메시(mesh)**: 참가자 N명이 서로 전부 직접 연결(N*(N-1)/2 개 연결).
  12명이면 66개 연결 — 화상회의 앱들이 통상 P2P 메시의 실용 한계로 보는
  "12~15명" 선에 딱 걸친다(그 이상부턴 SFU 같은 중계 서버가 사실상 필수).
  이 규모까지는 각 브라우저 CPU/대역폭에 문제없다(음성+가벼운 상태 데이터라
  화상회의보다 훨씬 가벼움). 서버 중계 비용이 전혀 안 든다는 게 가장 큰 장점 —
  이 저장소는 지금 서버 운영 경험/예산이 없다. **12명을 자주 꽉 채울 것 같으면
  이 한계를 미리 인지하고 있어야 한다** — 이후 인원이 더 늘 가능성이 있다면
  처음부터 SFU 방식(예: mediasoup 자체 호스팅, 또는 LiveKit 같은 관리형 서비스)을
  검토하는 게 나을 수 있다(비용/운영 부담은 커짐).

### 3-a. 시그널링 — 두 가지 선택지

WebRTC는 연결을 맺기 *전에* "내 연결 정보(SDP)를 상대에게 전달"할 통로가 필요하다.
이게 시그널링이고, 연결이 맺어진 뒤엔 필요 없다(그 뒤로는 P2P).

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. PeerJS 무료 클라우드 브로커** | 서버를 안 만들어도 됨 — `new Peer()` 한 줄. 이 저장소가 서버를 안 두는 원칙에 가장 가깝다. | 공용 무료 서버라 안정성/속도 보장 없음, 트래픽 제한 있을 수 있음, 외부 서비스 의존. |
| **B. 자체 소형 시그널링 서버**(Node + `ws`, 또는 Cloudflare Workers/Durable Objects) | 안정적, 우리가 통제 가능, 방(room) 코드 로직도 같이 둘 수 있음. | 이 저장소 최초로 "서버 배포"가 생긴다 — 호스팅 계정·배포 파이프라인이 새로 필요. |

**추천: A(PeerJS)로 시작.** 캐주얼 소규모 용도에 맞고, 나중에 문제가 생기면 그때
B로 바꿔도 클라이언트 쪽 코드(아바타/애니메이션/채팅 UI)는 거의 안 건드려도 된다 —
시그널링은 "연결 중개"라는 좁은 역할만 하므로 교체 비용이 작다.

### 3-b. NAT 통과 (STUN/TURN)

WebRTC가 각 참가자의 실제 접속 가능한 주소를 찾는 데 STUN 서버가 필요하다 —
Google의 무료 공개 STUN(`stun:stun.l.google.com:19302`)으로 대부분 해결된다.
다만 일부 네트워크(대칭형 NAT, 엄격한 사내망)는 STUN으로도 직접 연결이 안 돼서
TURN(중계) 서버가 필요할 수 있다 — TURN은 공짜가 잘 없다(트래픽을 실제로 중계하는
서버라 비용 발생). **1차 구현엔 TURN 없이 STUN만 넣고, 연결 실패 사례가 실제로
나오면 그때 TURN 도입을 검토**(과설계 방지).

## 4. 상태 동기화 설계

무엇을, 얼마나 자주, 어떤 채널로 보낼지가 네트워크 설계의 핵심.

| 데이터 | 채널 | 빈도 | 비고 |
|---|---|---|---|
| 위치/회전(x,z,yaw) | DataChannel(`unreliable`, UDP 느낌) | 초당 ~10회 | 유실돼도 다음 스냅샷이 금방 오므로 재전송 불필요 — 로블록스와 같은 이유. 받는 쪽은 보간(lerp)해서 부드럽게. |
| 상태(idle/walk/sit/eat/smoke/talk) | DataChannel(`reliable`) | 상태 바뀔 때만(이벤트 기반) | 애니메이션 클립 자체가 아니라 **상태 이름 문자열**만 보낸다 — 클립 재생은 각자 클라이언트가. |
| 텍스트 채팅 | DataChannel(`reliable`) | 이벤트 기반 | 순서 보장 필요. |
| 음성 | 별도 Audio Track | 연속 | WebRTC가 알아서 처리, 우리가 손댈 부분 없음. |

받는 쪽 렌더링 규칙(로블록스와 동일한 원리):
- **내 아바타**: 입력 즉시 반응(예측) — 서버가 없으니 보정할 대상도 없어서 오히려
  더 간단하다(진짜 로컬 그대로).
- **남의 아바타**: 마지막 두 스냅샷 사이를 보간해서 그림 — 뚝뚝 끊기지 않게.

**버그였다가 고침 — 늦게 들어온 사람과의 동기화 비대칭**: 상태를 "바뀔
때만" 보내는 설계라서, 새 피어가 방에 들어왔을 때 이미 그 방에 있던
사람이 마침 Sit/Smoke/이모트 중이었다면 "상태가 바뀐 시점"이 아니라서
새로 들어온 사람에게는 그 상태가 전달되지 않고 있었다(그 사람이 다음에
상태를 바꿔야 비로소 반영됨) — 닉네임/외형은 원래도 "누가 새로 들어오면
브로드캐스트" 로직이 있었는데 상태(state)만 빠져 있었다. `onPeerJoin`에서
닉네임/외형과 함께 현재 상태(state)와 위치(pos)도 같이 보내도록 고쳐서,
먼저 있던 사람과 나중에 들어온 사람 사이에 초기 동기화가 대칭이 되게
했다(`index.html`).

**버그였다가 고침 — 나간 사람이 계속 남아있음**: 탭을 그냥 닫는 등 정상
종료 신호 없이 사라지면 WebRTC 자체의 접속 끊김 감지가 느리거나 아예
안 걸리는 사례가 있어서, 이미 나간 사람의 아바타가 화면에 계속 남아있는
문제가 있었다. `lib/webrtc-mesh.js`에 `disconnect(remoteId)`를 추가하고,
`index.html`에서 각 상대로부터 마지막으로 뭔가 받은 시각(`av.lastMsgAt`)을
기록해뒀다가 2초마다 훑어서 6초 넘게 조용하면(위치는 원래 초당 ~10회
와야 정상) 우리 쪽에서 먼저 연결을 끊어버리는 감시 로직을 추가했다 —
위치 브로드캐스트 자체가 하트비트 역할을 겸하는 셈. 입장/퇴장은 화면
위쪽 토스트 + 우측 패널의 짧은 로그(`#eventLog`, 최근 8개)로 표시.

## 4-a. 하늘/바닥(공간이 무섭다는 피드백 대응)

배경이 단색 암흑(`0x1a1a1e`)이라 지평선이 안 보이고 "시커멓고 끝없어
보인다"는 피드백을 받음. 고친 내용(`index.html`):
- **하늘**: 큰 스피어(반지름 140, `BackSide`)에 버텍스 컬러로 위(어두운
  남색)→지평선(밝은 회청색) 그라데이션만 준다 — 텍스처/셰이더 없이 THREE
  기본 기능만으로. `fog:false`로 안개 영향은 안 받게.
- **안개/배경색을 하늘 지평선 색과 통일**(`SKY_HORIZON`) — 고전적인
  스카이박스 기법. 이걸 안 맞추면 "안개 색"과 "하늘 색"이 달라서 여전히
  경계가 보임.
- **바닥을 24→70으로 확대** + 안개 거리도 늘려서(20~70) 가장자리에
  닿기 전에 이미 안개에 가려지게 함 — "바닥 끝이 뚝 끊기는" 느낌 완화.
- **바닥 색도 어두운 아스팔트 회색(0x2a2a30)이라 무섭다는 추가 피드백** —
  따뜻한 톤의 광장 포장재 색(0xa89a80)으로 교체.

**버그였다가 고침 — 나간 사람의 담배 연기가 안 없어짐**: 담배 연기 입자는
세계 좌표로 흘러가야 해서 아바타 모델(`parts.root`)의 자식이 아니라
`scene`에 직접 추가하는 방식이었는데, 그래서 사람이 나갈 때
`scene.remove(model)`만으론 안 지워지고 있었다(게다가 `mixer.update()`가
더 이상 안 불리니 원래 있던 자동 소멸 로직도 멈춤 — 나간 사람이 마지막에
피우던 연기가 영구히 남는 버그). `spawnAvatar()`가 `dispose()`를 같이
돌려주게 해서 `onPeerLeave`에서 `scene.remove(av.model)`과 함께
`av.dispose()`도 호출하도록 고침(`index.html`).

## 5. 아바타 표현

- **형태**: 이 저장소 3D 게임들의 손님 캐릭터 빌더(예: 붕어빵 카페의
  `makeCustomerFigure`)와 같은 수준 — 캡슐 몸통 + 머리, 색상 몇 가지로 개인화.
  풀 스켈레탈 모션캡처 불필요.
- **상태별 애니메이션**: idle(숨쉬기), walk, sit(의자 오브젝트 위치에 스냅),
  eat(짧은 루프), smoke(짧은 루프 + 담배 프롭), talk(입 모양 대신 말풍선 아이콘
  또는 음성 활동 감지로 아바타 머리 위 표시등 — 립싱크는 과설계).
  - **sit 구현 완료**(`index.html`): 뼈대 없는 프리미티브 아바타라 진짜 앉는
    자세 대신 몸통을 낮추고 뒷발을 당기는 걸로 "앉은 느낌"만 낸다(`SIT_DROP`).
    벤치(`buildBench`, `placeBench`)를 클릭/탭하면 좌석 좌표로 스냅 + Sit
    상태 브로드캐스트, 이동 입력이 들어오면 자동으로 일어난다. **가까운
    벤치만 반응**(`MAX_SIT_TRIGGER_DIST`) — 멀리서 클릭했다고 거기까지
    끌려가면 어색하다는 피드백으로 추가한 제한.
  - **smoke 구현 완료**(`index.html`): 팔이 없어서 "손으로 든다"가 아니라
    입가에 담배 프롭을 붙여두는 걸로 대신함(`buildHamster`의 `cigarette`).
    벤치처럼 씬의 오브젝트를 클릭하는 게 아니라 오른쪽 아래 버튼(또는 F키)로
    아무 데서나 토글 — Sit과 같은 "이동하면 자동 해제" 규칙을 공유하도록
    `isSitting`을 `specialState`(null|'Sit'|'Smoke')로 일반화했다. 연기는
    별도 파티클 라이브러리 없이 작은 구체 메시를 주기적으로 만들어 위로
    흘려보내며 커지고 옅어지다 지우는 방식(아바타별 mesh pool). eat/talk는
    아직 구현 안 됨. **다음 라운드 예정**: 앉은 채로 담배 피우기(현재는 Sit과
    Smoke가 배타적 — 앉은 상태의 root 위치가 좌석 높이로 올라가 있어서
    같이 처리하려면 포즈 합성이 더 필요함), 담배 불붙이는 연출.
  - **감정표현 메뉴 구현 완료**(`index.html`): 가운데 아래 버튼(또는 E키)으로
    목록을 열고 고르면 정해진 시간만 재생 후 자동으로 Idle로 돌아간다(벤치/
    담배처럼 "움직이면 풀림"이 아니라 "시간이 지나면 풀림" — 다만 움직이면
    그 즉시 풀리는 것도 동일하게 적용). 무난한 걸로 5개 골랐다: 손 흔들기
    (Wave), 박수(Clap), 폴짝(Jump), 하트(Heart), 뻐큐(FlipOff — 요청받은
    항목, 팔/주먹/손가락 프롭을 담배처럼 몸통에 붙이는 방식). 팔 하나(`armPivot`)
    를 Wave/Clap/FlipOff가 포즈만 다르게 재사용. **버그 두 개 고침**:
    (1) `updateMyAvatar`의 "안 움직이면 Idle" 로직이 이모트를 매 프레임
    덮어써서 표시되자마자 사라지던 문제 — 이모트도 `specialState`로 등록해서
    해결(Sit/Smoke와 같은 매커니즘 재사용). (2) `#emoteMenu`에 `display:flex`를
    고정해둬서 `hidden` 속성이 안 먹던 문제(`#nameGate` 때와 같은 종류의 버그)
    — `#emoteMenu[hidden]{display:none}` 추가.
    앉아있는 동안은 다음 라운드 과제(위 smoke와 같은 이유).
  - **벤치 2인용 + 콜리전 + 앉기 전환 애니메이션**(`index.html`): 벤치가
    기본 2인용(`seatOffsets` 배열)이 됐고, 다른 아바타(나 자신 포함)가 이미
    앉은 좌석은 점유 판정으로 피해서 앉는다(`isSeatOccupied` — 서버가 없어서
    상대의 마지막으로 받은 상태/위치로 판정하는 근사치). 벤치/나무/카페
    테이블·스툴에 전부 충돌 박스(`userData.collider`)를 붙여서 통과해서
    걷던 문제를 고쳤다(`resolveCollisions` — 정밀 물리는 아니고 침투 축으로
    밀어내는 수준). 벤치를 클릭하면 텔레포트 대신 걷는 속도로 그 자리까지
    이동한 뒤(`sitAnim`) 앉는다.
- **커스터마이징 구현 완료**(`index.html`): 원래 계획보다 범위를 넓혀서
  몸통 색(6종, 밝기만 다른 파생색이라 ART_STYLE 1번 취지 유지) + 눈 모양
  3종(동그란/웃는/반짝) + 입 모양 3종(없음/냥이입/웃는입) + 머리 장식 3종
  (없음/삐침머리/리본, 색상 4종)을 우측 패널에서 바로 바꿀 수 있다. 전부
  지오메트리를 다시 만들지 않고 `applyAppearance()`가 재질 색만 바꾸거나
  미리 만들어둔 스타일 그룹의 visible만 토글하는 방식(감정표현의 armPivot
  패턴과 동일). `localStorage`에 저장해서 재방문 시 유지, 바뀔 때마다
  `appearance` 메시지로 브로드캐스트해서 남들 화면에도 반영됨. 의상/액세서리
  시스템은 필요성이 더 확인되면 확장.
  - **버그**: 머리 장식/입 소품을 머리 구(반지름 0.3) 표면 안쪽에 두면
    파묻혀서 안 보임(z-fighting) — 눈/코처럼 표면 반지름보다 살짝 바깥에
    둬야 한다는 걸 몇 번 겪고서야 알아챔. 다음에 얼굴/머리에 뭘 더 붙일
    땐 이 반지름(0.3) 밖인지부터 확인.

## 6. 룸(공간) 모델

**(결정 변경 — 최초 "6자리 코드로 방 입장" 안은 폐기하고 아래 오토 인스턴싱으로
확정.)**

- **로비 화면 없이, 오토 인스턴싱**: 사이트 접속 → 매칭 서버가 "현재 인원이
  정원(12명) 미만인 방"에 자동 배정. 그 방이 꽉 차면 새 인스턴스(#2, #3…)를
  자동 생성해서 그쪽으로 보낸다. 코드를 직접 입력해서 들어가는 개념이 없다 —
  애초에 사람이 많이 몰릴 사이트가 아니라서 "누구랑 매칭될지 고른다"는 로비
  UI 자체가 불필요하다는 결론(방 하나 꽉 차면 또 다른 방에서 놀면 됨, 로블록스
  서버 인스턴스와 같은 개념이되 "로비"는 생략).
- **이게 되려면 시그널링이 3-a의 A안(PeerJS 무료 브로커 단독)만으론 부족하다** —
  브로커는 "누가 누구와 연결할지"만 중개하고 "지금 어느 방에 몇 명 있는지"
  상태를 갖고 있지 않기 때문. **작은 매칭 서버(방별 인원수 카운트 + 빈 방
  배정)가 필요** — PeerJS 브로커는 그대로 연결 중개용으로 쓰되, 그 앞단에
  "어느 방(peer id 네임스페이스)으로 갈지"만 정해주는 가벼운 서버리스
  함수/Durable Object 하나를 얹는 형태를 우선 검토(3-a B안과 사실상 같은
  방향 — CLAUDE.md "정적 파일 + 빌드 없음" 예외 범위가 여기까지 넓어짐을
  명시적으로 인지하고 간다).
- host 개념 없이 **동등한 피어**로 시작(메시 구조에 자연스럽게 맞음) — 방장 권한이
  필요해지면(예: 강퇴) 그때 추가.

### 6-a. 사용자 식별/이름

- **IP 기반 식별은 채택 안 함** — NAT 뒤에 여러 명이 같은 공인 IP를 공유하는
  경우가 흔하고(모바일 통신사, 회사망), IP 자체도 세션마다 바뀔 수 있어서
  식별자로 못 쓴다.
- **구글 로그인도 채택 안 함** — OAuth 플로우, 동의 화면, 계정 연동 상태 관리가
  붙는데 이 프로젝트 규모(친구들끼리 캐주얼하게 쓰는 공간)에 비해 과하고,
  "로그인/계정 불필요"라는 이 저장소의 기존 원칙(위 6번, `web-games`와 같은
  결)과도 어긋난다.
- **채택: 입장 시 닉네임을 직접 입력**(서버 저장 없이 `localStorage`에만 남겨서
  다음 방문 때 재입력 안 해도 되게) — 인증이 필요한 게 아니라 "누가 누군지
  화면에 표시"만 하면 되는 용도라 이 정도로 충분하다. 같은 방(인스턴스) 안에서
  닉네임이 겹치면 접속 시점에 숫자를 붙여 구분(예: "민지", "민지(2)") — 이것도
  서버 조회 없이 메시 핸드셰이크 때 다른 피어들이 이미 쓰는 이름과만 비교하면
  된다.

## 8. 구현 순서 (마일스톤)

1. **로컬 프로토타입**: 네트워킹 없이 아바타 하나 + 상태 전환(걷기/앉기/먹기/담배)
   애니메이션만 완성 — Three.js만으로 검증.
2. **같은 브라우저 2탭 WebRTC 연결**: `localhost`에서 탭 2개 띄워 PeerJS로 연결,
   위치 동기화 + 보간이 실제로 부드러운지 확인.
3. **원격 연결**: 다른 기기/네트워크에서 접속해 STUN 통과 확인, 연결 실패율 체크.
4. **음성 추가**: Audio Track 붙이고 mute/unmute UI.
5. **채팅 텍스트 + 룸 코드 시스템** — 텍스트 채팅 구현 완료(`index.html`).
   룸 코드는 이후 오토 인스턴싱으로 대체 결정(6번 참고). 우측 패널의
   `#chatInput`에서 Enter로 전송, `{type:'chat'}` 메시지로 브로드캐스트.
   전용 3D 말풍선을 새로 안 만들고 머리 위 닉네임 라벨을 몇 초간
   "닉네임: 메시지"로 바꿔치기하는 걸로 말풍선 역할까지 겸하게 했다
   (`showChatBubble`). 채팅 입력 중엔 WASD/F/E 게임 단축키가 안 새게
   `isTypingInField()`로 막음(그 전까진 필요 없었는데 채팅창이 상시
   노출되면서 필요해짐).
6. **폴리시**: 아바타 색상 커스터마이징(완료 — 5번 참고), 담배 연기
   파티클(완료 — 5번 참고) 같은 디테일.

각 단계는 이전 단계가 실제로 동작 확인된 뒤에만 다음으로 — 특히 2→3(로컬 성공이
원격 성공을 보장 안 함, NAT 환경이 진짜 변수)은 반드시 실제 기기 두 대로 검증한다.
